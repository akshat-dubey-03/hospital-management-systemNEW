# Index review and EXPLAIN comparison (Phase 11)

Script: `sql/12_indexing_explain.sql`. Evidence: `results/12_indexing_explain_run.txt`, run on the disposable database `medicore_dbms_p11b` with PostgreSQL 15.15, `jit = off` and no parallel workers. Permanent change: migration `20261011140000_dbms_patient_schedule_index`, generated by `prisma migrate diff` from `schema.prisma`.

## Existing indexes on `appointments` (before)
`appointments_pkey (id)`, `appointments_patientId_idx (patientId)`, `appointments_doctorId_idx (doctorId)`, `appointments_appointmentDate_idx (appointmentDate)`, `appointments_doctorId_appointmentDate_idx (doctorId, appointmentDate)`, and the partial unique `appointments_active_doctor_slot_unique (doctorId, appointmentDate, startTime) WHERE status not cancelled`.

## Query chosen
The patient dashboard (`dashboard.service.js`) runs
`SELECT … FROM appointments WHERE "patientId" = $1 ORDER BY "appointmentDate", "startTime"`.
It then filters "upcoming" in JavaScript. A bounded variant, "next 5 upcoming", is also measured:
`… AND "appointmentDate" >= $2 ORDER BY … LIMIT 5`.

## Test data
Generated at run time and not committed: 40 synthetic doctors × 300 days × 16 slots, giving **192,015 appointments**. These span 2,006 patients, about 96 each; the target patient has **98** rows. IDs are deterministic and inserts use `ON CONFLICT DO NOTHING`, so the script can be re-run. Step 0 recreates the pre-migration index layout, so "before" is always the same configuration.

## Proposed index and why
`CREATE INDEX "appointments_patientId_appointmentDate_startTime_idx" ON appointments("patientId", "appointmentDate", "startTime")`, replacing `appointments_patientId_idx`.

- **Column order.** Equality column first (`patientId`), then the range/sort columns in `ORDER BY` order. For one patient, the entries are already sorted by date and then time. Only a *leftmost prefix* can be used: `patientId`, or `patientId + appointmentDate`, or all three. A predicate on `appointmentDate` alone cannot use it (shown in 5b: the planner uses `appointments_appointmentDate_idx`).
- **Why the old index is dropped.** Its single column is the composite's leftmost column, so every `patientId = $1` lookup still has an index. This includes the FK check when a patient row is deleted (shown in 5a). Keeping both would cost write time and space for no read benefit. The migration creates the new index *before* dropping the old one.

## Before / after (actual output)

| Query | Before | After |
|---|---|---|
| Full history, 98 rows, `ORDER BY` | Bitmap Index Scan `patientId_idx` → Bitmap Heap Scan (98 pages) → **Sort** (quicksort 34 kB); est. 95 / actual 98 rows; 100 buffers; **0.410 ms** | Bitmap Index Scan on the **composite** → Bitmap Heap Scan → **Sort**; est. 95 / actual 98; 101 buffers; **0.305 ms** |
| Next 5 upcoming (`>= 2026-10-10 … LIMIT 5`) | **BitmapAnd** of `patientId_idx` (98 rows) and `appointmentDate_idx` (14,088 rows) → heap → **Sort**; est. 7 / actual 8; 22 buffers; **1.102 ms** | **Index Scan** on the composite with both conditions in `Index Cond`, **no Sort**, stops after 5 rows; 8 buffers; **0.099 ms** |

**Honest reading.**
- **Full-history query (what the dashboard runs today):** the index does **not** change the plan shape. The patient's 98 rows sit on 98 different heap pages, so a bitmap heap scan plus an in-memory sort of 98 rows remains cheapest, and the planner correctly keeps it. The 0.41 → 0.31 ms difference is within run-to-run noise; no improvement is claimed.
- **Bounded upcoming query:** about 11× faster, 22 → 8 buffers, and no sort. The index returns the rows in order and the `LIMIT` stops early. Before, PostgreSQL had to combine two bitmaps, one of them 14,088 entries, and sort.
- **Cost:** the composite index is **9,336 kB** against 1,552 kB for the single-column one, at 192k rows. That is wider keys (uuid + date + varchar) and more write work per insert or update of these columns.
- **Recommendation:** the full benefit needs the dashboard to push the upcoming filter and `take` into the SQL query instead of filtering in JavaScript. That application change was not made here (out of scope).

## Legitimate sequential scan
The admin dashboard counts active appointments with `status IN ('BOOKED','CONFIRMED')`. In the synthetic data that matches 12,680 rows and removes 179,335. A whole-table aggregate over a low-cardinality status column is done most cheaply by a **Seq Scan** (5c), so no status index is proposed.

## Other observation (not changed)
`appointments_doctorId_idx (doctorId)` is a leftmost prefix of `appointments_doctorId_appointmentDate_idx` and is likely redundant for the same reason. It was left in place because this phase measured only the patient query.

## Verification of the permanent change
`prisma migrate deploy` applied the migration. `prisma migrate diff` reports no difference, both from migrations and from the live test DB. The Jest suites pass 23/23. `01_ddl.sql` was updated to the final index layout.
